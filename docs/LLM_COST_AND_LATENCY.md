## 3. 结论：分两个场景，结论相反

### 3.1 当前（R3.1/R3.2 = **盘后** 15:35 跑）—— 无问题 ✅
盘后链对实时性**没有要求**，21 s/链完全可接受。**当前不存在「决策滞后」问题。**

### 3.2 R4 盘中实时（09:30–15:00 逐分钟）—— **串行绝不可行** ⚠️
- 单只 p50 **2.1 s**、p90 **4.1 s** → 分钟级 bar 收盘后要 2–4 s 才出判定
- 50 只**串行** ≈ **46 s** → **跨分钟**，直接失效
- 若对候选池每只每分钟都调：`50 × 240 = 12,000 次/日` ≈ **1.1×10⁷ tokens/日**
  → 延迟与成本**双不可行**

## 4. 由数据推出的架构约束（**R4 必须遵守**）

| # | 约束 | 依据 |
|---|---|---|
| 1 | **LLM 绝不出现在秒级路径上** —— tick 守护必须**纯机械** | p90 单只 4.1 s，秒级要 100 ms 级 |
| 2 | **机械硬规则层实时跑**（微秒级），它负责「明确档位」的直接判定 | 延迟差 4 个数量级 |
| 3 | **LLM 只作异步咨询**：只对「机械层判定为边界/冲突」的**少数**标的咨询，结果用于**下一分钟** | 把 50 只降到个位数 |
| 4 | **缓存是把它拉进分钟级的关键**（协议已内建「同标的同状态 5 分钟内复用」） | 5 分钟内分时状态变化小 |
| 5 | ⚠️ **但盘中缓存命中率尚未实测** —— 现有 117/123 是**跨运行的相同快照**命中，**不等于**盘中 5 分钟窗的命中率 | 不得拿它当盘中可行性证据 |
| 6 | D6 三档里**只有 A/C 边界需要裁量**，明确档位可纯机械定 → 可进一步削调用量 | 三档枚举自身结构 |

## 5. schema 失败根因与修复（2026-09-13 实测闭环）

### 5.1 ⚠️ 先纠正一个错的结论：「换模型」不是根因
- 实测 `GET /models`：**可用模型只有两个** —— `deepseek-flash`（在用）与 `deepseek-v4-pro`
- ⭐ **`deepseek-chat` 与 `deepseek-reasoner` 返回的 `model` 都是 `deepseek-flash`**
  —— 它们**不是两个模型，而是同一底座的两种「应答模式」**：

| 模式 | reasoning | completion tokens | 实测 |
|---|---|---|---|
| `deepseek-chat` | 无 | **30** | 直答 |
| `deepseek-reasoner` | 756 字符 | **211**（**7×**） | 先推理再答 |

- 遂把默认模式从 `deepseek-reasoner` 改为 `deepseek-chat`（`llm.DEFAULT_MODEL`，可用
  `EVOALPHA_LLM_MODEL` 覆盖）→ **降级率 12.5% → 12.6%，没有改善** ⇒ **换模型不是根因**。

### 5.2 真根因（两类，均与模型无关）
| 类型 | 数 | 根因 |
|---|---|---|
| **`出现未允许的键: ['discretionId']`** + `缺必填键 discretion_id` | **9** | ⭐ **模型把 `discretion_id` 写成驼峰** —— prompt 对键名的约束不足 |
| `parse_failed`（`content` 空/被截断） | 13 | JSON 解析失败 |

### 5.3 修复与验证
**修 prompt**（`llm.build_prompt`，模板 **`d6-v2`→`d6-v3`**、**`d8-v1`→`d8-v2`** ——
`build_prompt` 为两裁量点共用，**必须同步升版**）：
1. ⭐ **「键名逐字照抄」硬约束** + **反例**（`discretionId` / `discretion-id` / `DiscretionId` 一律不接受）
   + **禁止额外键**（`sym` / `rationale` / `note` / `model`）
2. **`choice` 与 `score` 自洽**（`C_reject` 时 `score` 必须 ≤0.3；`score` ≥0.6 不得选 `C_reject`）
3. **`reason` 必须单行**、≤120 字符

**抽样验证（8 例，覆盖此前失败较多的边界样本）**：**schema 通过 8/8 = 100%**
（此前同一场景 12.6% 失败）；且判定质量改善：
- **`605006` 山东玻纤 → `A_optimum` score 0.72** —— 正是选手原话「①**最优档**：有量+一步步向上」
- `603113` 金能科技 → `C_reject` 0.15 —— 与选手「③弃：破均价线」一致
- `score`/`choice` 自洽（`C_reject` 时 ≤0.3）

⚠️ **仍待观察**：`parse_failed` 13 例（`content` 空/截断）在 chat 模式下仍出现，未在本轮闭环；
建议下轮把 `schema_failed` 率**纳入日常监控**（落盘已有 `status` 字段，可直接聚合）。
